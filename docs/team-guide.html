SECTION 1

What we're building

A system that looks at a flight which has just taken off and predicts how many minutes late it will arrive.

We have 5.8 million real flights from every US domestic route in 2015 — who flew them, from where, to where, when they were scheduled, and when they actually left and landed. That is far too much data for Excel or ordinary Python, so we use Apache Spark, which splits the work across all the cores on a machine (and, in industry, across many machines).

We answer two questions about each flight:

  • How late will it be? A number in minutes — a regression problem.
  • Will it be badly late? More than 30 minutes, yes or no — a classification problem.

This is coursework marked out of 100: 35 marks for a written report explaining the mathematics, and 65 marks for working code that meets a specific brief — custom Spark components, dimensionality reduction, five competing algorithms, experiment tracking, and live scoring of streaming data.

Where the project stands today

The environment, the data preparation and the custom components are finished and tested. The full model-training run is written and proven on small samples but has not yet been run at full scale — that is the biggest remaining job. The report's theory is complete; its results section is waiting on that run.

SECTION 2

Words you'll see

Open any of these when you hit the term. Nothing here assumes you've used Spark.

Spark / PySpark

Spark is a tool for processing data too big for one program to hold in memory. It breaks a table into chunks, works on them in parallel, and combines the results. PySpark is how you drive Spark from Python.

One important habit: Spark is lazy. When you write a transformation nothing happens; it only runs when you ask for a result (a count, a save). This is why a line that "looks instant" can suddenly take a minute.

DataFrame

A table with named columns, like a spreadsheet or a SQL table — except it may be spread across many chunks and many CPU cores. Everything in this project is a DataFrame.

Pipeline, Transformer, Estimator

A Pipeline is an ordered list of data-preparation steps ending in a model, so the exact same preparation is applied during training and later during prediction. This matters enormously — most real bugs come from preparing training and live data differently.

A Transformer just changes data (e.g. "multiply this column by 2"). An Estimator first learns something from the training data and then produces a Transformer that applies what it learned (e.g. "work out the average, then subtract it"). The difference is central to Section 6.

Training split / test split

We hide 20% of the flights from the model while it learns, then measure it on those unseen flights. Otherwise we would only be proving it can memorise, not predict.

Data leakage

When the model accidentally gets information it would not have in real life. It then scores brilliantly in testing and fails completely in production.

Our dataset contains a perfect trap for this — see Section 6, rule 1. It is the single most important idea in the project.

Cross-validation

Instead of testing once, split the training data into 5 parts, train on 4 and test on the 5th, and rotate. You get a more trustworthy score and can compare model settings fairly. It costs 5× the compute, which is why our training run takes hours.

R², RMSE, AUC

R² — how much of the variation the model explains. 1.0 is perfect, 0 is no better than always guessing the average. Ours is about 0.93.

RMSE — typical error in the model's own units. Ours is about 10.5 minutes.

AUC — for yes/no questions, the chance the model ranks a genuinely late flight above an on-time one. 0.5 is a coin flip; ours is about 0.95.

PCA (dimensionality reduction)

A method for squeezing many columns into a few that carry most of the information. The brief requires it. On our data it works poorly — it keeps only 28% of the information — so we train every model twice, with and without it, and report the difference honestly. That comparison is worth marks.

MLflow

A record-keeper for experiments. Every training run logs its settings, its scores and the trained model itself, so results are reproducible and comparable instead of scribbled in a notebook. It also stores the winning model in a "registry" and marks it as the production version.

Streaming

Scoring flights as they arrive rather than in one big batch. We demonstrate it by dropping small files into a watched folder; the job picks them up and predicts within seconds, using the exact model saved during training.

SECTION 5

How the pipeline works

Raw flights go in one end; a delay prediction comes out the other. Every step runs in the same order during training and during live scoring — that's the whole point of a pipeline.

Step 1Clean upTrim absurd values learned from training data only.
Step 2Add featuresDistance between airports, how tight the schedule is.
Step 3EncodeTurn airlines and airports into numbers a model can use.
Step 4Combine & scaleMerge into one vector, put every column on a comparable scale.
Step 5PredictOne of five algorithms produces the delay estimate.

The five algorithms we compare

The brief names all five, and they are trained on identical data so the comparison is fair: Linear Regression, a Generalised Linear Model, Linear SVC, Random Forest and Gradient-Boosted Trees. The first three draw straight-line relationships; the last two build many decision trees and combine them.

Each is trained twice — once with PCA and once without — giving 14 runs in total. That's why the full training run takes hours.

PCA variance kept28.5%Squeezing the columns loses most of the information — so we report both.
SECTION 6

Rules: don't undo these

Each of these looks like a mistake if you don't know the reason. All of them were arrived at by measurement, and reverting any one measurably breaks the project.

Rule 1 — the model must never see the future

The dataset contains five columns that break down why a flight was late. Add them up and you get the answer exactly. A model given them scores about 0.99 and is completely worthless, because at take-off those columns don't exist yet.

They are deleted in code, with a check that fails loudly if one sneaks back. If you ever see a score near 0.99, something has gone wrong — don't celebrate it.

Rule 2 — leave departure delay alone

How late a plane left is by far the best clue to how late it will arrive. Two reasonable-looking "tidy-ups" were tried on that column and both destroyed it: capping extreme values threw away the 12.8% of flights that matter most, and rescaling it broke the straight-line relationship the model relies on.

Passed through untouched: R² 0.937. Capped: 0.390. Rescaled: 0.409. It stays raw.

Rule 3 — learn from training data only

Our custom components learn their settings (cut-off values, category averages) during training and then freeze them. Writing them the simpler way — recalculating each time they run — would quietly let test data influence the result, and would behave differently on every batch of live data.

Rule 4 — keep both PCA and non-PCA versions

PCA is required by the brief but performs poorly here. Training both ways lets us satisfy the requirement and show what it costs — and only the non-PCA version can tell us which features actually mattered.

The full reasoning, with the mathematics, is in docs/REPORT.md. Please read the relevant part before changing any of the above.

SECTION 8

When it breaks

Every failure below is one we actually hit. Type an error message to filter.

Everything fails the moment I run anything

You almost certainly forgot to load the environment. Run source ./env.sh (or . .\env.ps1) in this terminal — it doesn't carry over between windows.

"Python worker exited unexpectedly" / EOFException

You're on Python 3.12. Spark 3.5 launches its helper process, the process exits silently, and every task dies. Confusingly, some Spark features keep working, so it looks like a different problem entirely.

Fix: rebuild the environment on Python 3.11 (step 04). This is not optional.

ModuleNotFoundError: typing.io

You're running the system Python (3.13 or newer) instead of the project one. Load the environment first; it selects the correct interpreter.

Java errors, or Spark won't start at all

JAVA_HOME is pointing at a Java version Spark doesn't support. The environment file points it at the project's own Java 17 — make sure you unpacked the JDK into .jdk/ as in step 05.

NativeIO$Windows.access0 when saving a model

hadoop.dll is missing from .hadoop/bin/. Windows needs it for Spark to write files. Note that winutils.exe alone is not enough, and the version must match the one Spark ships with (3.3.5) rather than any Hadoop you have installed.

NotConvergedException during PCA

Happens on very small samples: a category is missing from a fold, its column becomes constant, and the maths breaks down. The pipeline already guards against this. If you see it, you've probably reordered or removed a pipeline stage — put it back.

Training seems frozen with no output

Probably fine. Spark prints progress bars that don't flush cleanly, and long runs write to a log file instead. Check the log directly rather than watching the terminal, and give any full run a couple of hours before worrying.

My scores look amazing (R² near 0.99)

That's a bug, not a breakthrough. A forbidden column has got back into the features — see Section 6, rule 1. Expect roughly 0.85 to 0.93.

My scores look terrible (R² near 0.48)

Something is transforming the departure delay column again. See Section 6, rule 2.

Nothing happens in the streaming demo

Start the scoring job first, then generate events in a second terminal — it only reacts to files that arrive after it starts watching. Both terminals need the environment loaded.

No match. Ask in the group chat and we'll add it here.

How we work

Branches

All work goes on test. main deliberately holds only the README and the ignore file. Please don't push without saying so — history has been rewritten once already and a surprise push can undo it.

Before you commit

Run both gates. If either fails, something upstream broke.

python scripts/smoke_test.py         # expect 5/5
python scripts/test_transformers.py  # expect 8/8

Two habits that saved us real time

  • Measure before you "fix" a score. Two sensible-looking improvements to the same column both made things worse. A five-minute comparison settled it where argument couldn't.
  • Open the charts you generate. A chart can save successfully and still be unreadable — one had its legend sitting on top of the numbers, invisible until someone actually looked at the image.
