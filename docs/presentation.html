A1

Scaling mathematics and distributed sparse operations

Feature scaling looks like a solved, mechanical step. On a distributed sparse matrix it is neither: one boolean flag changes the memory complexity of the entire pipeline, and the choice of transform can destroy the strongest predictor in the dataset.

A1.1 Standardisation versus range scaling

Z-score. For feature j with mean μj and standard deviation σj:

Standardisation — StandardScaler
zij = xij − μj σj

Yields mean 0, variance 1. The transform is unbounded, so outliers survive it — a value 40 standard deviations out is still 40 afterwards.

Min–max. Mapping onto a guaranteed range, by default [0, 1]:

Range scaling — MinMaxScaler
xscaledij = xij − xminj xmaxj − xminj (max − min) + min

The bounded output suits distance kernels — but the mapping is defined by exactly two order statistics, so a single extreme value sets the denominator.

Concrete on this dataset

DEPARTURE_DELAY runs from −82 to 1,988 minutes — one aircraft delayed 33.1 hours — against a median of −2. Min–max divides every ordinary flight by a range that single row set: 85.6% of all 5.7M flights land below 0.05, 98.1% below 0.10, and just 43 rows sit above 0.7.

Why this reaches the ElasticNet arm

The compression is not uniform — each column is squeezed by whatever outlier it happens to carry. Interquartile span as a fraction of each column's own scale:

columnmin–maxx / σ
DEPARTURE_DELAY0.00580.325
TAXI_OUT0.03570.901
DISTANCE0.13991.138
SCHEDULED_TIME0.12571.168
widest : narrowest24×3.6×

Under min–max, DEPARTURE_DELAY — the most predictive feature in the dataset, r = 0.9446 — gets a usable range 24× narrower than DISTANCE, purely because of one 33-hour delay. The ElasticNet penalty charges every coefficient at the same rate regardless of its feature's scale, so a feature compressed by a factor c needs its coefficient to grow by 1/c for the same effect — and is then billed 1/c times harder under L1 and 1/c2 under L2. Min–max would regularise the best feature toward zero ~24× (L1) or ~576× (L2) faster than DISTANCE, for reasons unconnected to its predictive value. Standardisation sets every σ to 1, so the penalty compares like with like.

Both transforms are affine in x, so neither changes the shape of a distribution — neither one fixes skew. That is what A1.3 is for.

Degenerate columns. If σj = 0 the z-score is undefined. Spark defines it as 0 rather than failing — numerically safe, but with a downstream consequence we hit in practice (A2.3).

A1.2 Why centering is dangerous on sparse vectors

A SparseVector stores only its non-zero entries, as parallel index and value arrays. Its memory is O(nnz), not O(n). Centering breaks that representation outright. For any feature with μj ≠ 0, a structural zero maps to:

The centering trap
0 − μj = −μj ≠ 0

So every zero becomes an explicitly stored non-zero. Sparsity is not reduced — it is destroyed, and the vector must be materialised dense.

The cost is a direct function of the one-hot expansion in the assembled vector:

Assembled feature vector — density budget
QuantityValue
Total feature slots after assembly80
Slots from one-hot groups60
Non-zeros per row23
Density28.75%
Cost of centering2.0×

A 2.0× increase in shuffle volume, cache footprint and GC pressure across 5.7M rows — and it scales with the worst case, not the average. Push ROUTE (4,635 levels) through one-hot instead of target encoding and density falls below 1%, making centering a ~100× penalty.

How withStd avoids it

Scaling is multiplicative, and zero is a fixed point:

Sparsity-preserving scaling
xij ↦ xij σj 0 ↦ 0

The sparsity pattern survives exactly; only stored values change. Spark rescales in place, touching O(nnz) entries.

Hence withMean=False, withStd=True is set deliberately, not left as an untouched default. The cost — features scaled but not centred — is irrelevant to the tree ensembles (splits are scale- and location-invariant) and is absorbed by the fitted intercept in the regularised linear models.

A1.3 Compress, truncate, or neither

Affine scaling cannot fix skew, so heavily right-skewed columns are compressed first. Two properties matter: the map is monotonic, so ordering is preserved and tree splits are unaffected; and its derivative 1/(1+x) shrinks as x grows, so large values are pulled in far harder than small ones.

Signed log — defined on all of ℝ
f(x) = sign(x) · ln(1 + |x|)

Plain ln(1+x) is undefined for x ≤ −1, and DEPARTURE_DELAY is negative for every early flight. The signed extension is odd, monotonic across zero, continuous with f(0) = 0 — so sparsity still survives — and compresses both tails alike.

Truncation and compression are different tools. Tukey fences [Q1 − 1.5 IQR, Q3 + 1.5 IQR] remove tail information; log compression retains it with rank intact. But the lesson from this dataset is that sometimes the right answer is neither.

Measured — two wrong fixes before the right one

DEPARTURE_DELAY and arrival delay are very nearly linear: correlation 0.9446, slope near 1. Clipping first dropped that to 0.614, capping achievable R2 near 0.38. The obvious repair — signed log instead — was also wrong: a monotone nonlinear transform destroys exactly the structure a linear model exists to exploit.

LinearRegression on a 2% sample — isolated A/B
Treatment of DEPARTURE_DELAYR2
Clipped only — first attempt0.390
Signed log only — second attempt0.409
Clipped + signed log0.409

The raw column carries essentially all the signal; both derived views add nothing measurable on top of it. The general principle: skew is a reason to compress, contamination is a reason to truncate, but a feature that is large, genuine and linearly related to the target needs neither. Reaching for a transform because a distribution looks untidy is how signal gets destroyed.

DISTANCE is the case that does want compression — its fitted upper fence lands at 2,091 miles, which would fold every transcontinental flight into one value. TAXI_OUT is the case that genuinely wants truncation, where extreme values really are operational anomalies.

A2

Distributed PCA mechanics

A2.1 What is actually distributed

PCA needs the eigendecomposition of the covariance of an m × n matrix — here m = 5,704,000 and n = 77. The essential asymmetry is that m is enormous and n is small, and Spark's design follows entirely from it.

The Gramian decomposes as a sum over rows
A⊤A = Σ i=1m  ai ai⊤

Each term is n × n. Every executor scans only its own partition, accumulating a local n × n matrix; partial sums are combined by treeAggregate, whose depth is logarithmic in the partition count.

Two routes through RowMatrix — and which one this pipeline takes

RowMatrix.computeSVD accepts a mode of auto, local-svd, local-eigs or dist-eigs. Under dist-eigs it calls EigenValueDecomposition.symmetricEigs, whose signature takes a function DenseVector => DenseVector rather than a matrix — ARPACK’s implicitly-restarted Lanczos, needing only the product Aᵀ(Av) from the distributed multiplyGramianMatrixBy. On that path no n × n matrix is ever materialised. That is precisely the mechanism the specification asks about.

spark.ml’s PCA does not call it. It uses computePrincipalComponentsAndExplainedVariance, which has no mode parameter and one path: build the covariance via computeCovariance, then a local Breeze SVD on the driver. So the PCA arms no longer use it — they run custom_transformers.RowMatrixPCA, which calls computeSVD with the mode named explicitly, reaching the six-argument Scala overload through py4j because PySpark's Python wrapper exposes no mode and "auto" picks a local path at n < 100.

It centres the rows first, since computeSVD decomposes whatever it is given and PCA needs the covariance. Against spark.ml's PCA the components then match at |cos| = 1.0 and the explained variances to five decimals — the mechanism changed, the numbers did not.

The price: dist-eigs runs one distributed pass per Lanczos iteration, 19 Spark stages on a small probe against the Gramian route's one. Measured on the real 80-column vector that is 6.7× at 50k rows and 8.0× at 200k for the PCA stage. We ship it as the default regardless, because it is the only mode that satisfies the specification's wording — local-eigs and local-svd both call computeGramianMatrix.

The case for the cheaper mode is that at n = 77 the covariance is 46 KB — but that argument picks an algorithm from the size of one sample. The width is 80 only because ROUTE is target-encoded: one-hot it instead and n = 4,703 with a 169 MB covariance; add TAIL_NUMBER and it is 9,599 and 703 MB on the driver, which is a crash rather than a slow path. dist-eigs holds one 616-byte vector at any width. The 6.7–8.0× buys the removal of that cliff, not speed — --svd-mode local-eigs stays available for iteration.

A2.2 From SVD to principal components

Why the right singular vectors are the components
A⊤A = VΣ⊤U⊤UΣV⊤ = VΣ2V⊤

Using U⊤U = I. So the columns of V are the eigenvectors of the Gramian — the principal directions — with eigenvalues λi = σi2. The projection AVk is a per-row map, so it is distributed with no shuffle at all.

Explained variance ratio
EVR(k) = Σi=1k λi Σj=1p λj

The denominator equals tr(A⊤A), the sum of per-feature variances — so with standardised inputs it is simply p.

Measured — and unflattering to PCA

Ten components retain only 28.5% of the variance of the 77-dimensional space, and the cost lands directly on the models: linear regression scores R2 = 0.9289 on the full feature set against 0.7034 through PCA(k=10).

That is not a bug — it is what PCA does to this feature space. Most dimensions are one-hot indicators: close to mutually orthogonal, individually low-variance, with little linear redundancy to exploit. PCA pays off when features are strongly correlated; one-hot expansions of independent categoricals are close to the opposite case. The scree curve shows exactly that — no elbow, just a slow decline.

A2.3 A singular covariance, in practice

The driver-side SVD is not merely a scaling footnote — it is a failure mode. The first tournament run died with breeze.linalg.NotConvergedException inside PCA.fit. The causal chain is worth tracing, because every link is individually reasonable:

Failure chain — four correct behaviours composing into a crash
#Step
1OneHotEncoder(handleInvalid="keep") reserves a slot for unseen categories
2On a small CV fold that slot never fires — the column is constant
3StandardScaler maps a zero-variance column to all zeros (A1.1)
4The covariance matrix is singular; LAPACK fails to converge

Diagnostically the feature matrix contained no NaN and no Inf — 3 of 80 columns were identically zero. The fix, a VarianceThresholdSelector ahead of PCA, is both the repair and the correct modelling choice: a constant feature carries no information by definition.

Note the interaction

The bug surfaced only at small sample sizes, because on the full data most categories appear in every fold. Testing at reduced scale is what exposed it — the cheap run was not merely faster, it was strictly more informative.

A3

Parametric models versus tree ensembles

A3.1 ElasticNet regression

Spark's LinearRegression objective
J(β) = 12n Σi (yi − xi⊤β)2 + λ [ α‖β‖1 + 1−α2 ‖β‖22 ]

with regParam = λ and elasticNetParam = α.

The two penalties do different jobs. The ℓ2 term adds λ(1−α)I to the normal equations, so X⊤X is invertible even when it would otherwise be singular — buying stability against the collinearity our features have by construction (DISTANCE, GC_DISTANCE_MI and SCHEDULED_TIME are near-collinear).

The ℓ1 term is not differentiable at zero; its subgradient is a constant ±λα, applying the same push regardless of coefficient size and driving small coefficients exactly to zero. That is genuine selection, not just shrinkage.

Why mix them: lasso alone, given a group of correlated features, picks one arbitrarily and zeroes the rest — and which one it picks is unstable across resamples. The ridge component restores the grouping effect, so correlated features shrink together. Because ℓ1 is non-smooth, Spark optimises with OWL-QN rather than plain L-BFGS.

A3.2 Generalised linear models and link functions

The link connects predictor to response
g(𝔼[Y]) = Xβ

Ordinary least squares is the special case of a Gaussian response with the identity link. The link earns its keep when the identity is wrong about the response's support or its mean–variance relationship.

Variance functions — why the family choice matters
FamilySupportV(μ)Suits
Gaussianℝ1constant absolute error
Poisson0, 1, 2, …μcounts; dispersion grows with level
Gamma(0, ∞)μ2constant relative error

Measured — a variance function, demonstrated the hard way

The Gamma/log arm failed violently: R2 = −207, RMSE 568.90 against MAE 10.80 — a 53× ratio where ~1.3× is normal, i.e. a handful of astronomically large exp(x⊤β) predictions dominating the squared error.

Gamma's V(μ) = μ2 amplifies exactly these tail excursions, where Poisson's V(μ) = μ grows only linearly. Switching family moved R2 by more than two orders of magnitude — to −0.036. Still the weakest regressor, because a log link models a multiplicative response while arrival delay is additive in departure delay. The mismatch is structural, not a tuning failure.

A3.3 LinearSVC and the soft-margin hinge loss

A separating hyperplane has geometric margin 2/‖w‖, so maximising the margin means minimising ‖w‖2. Real data is not separable, so slack variables permit violations. The constraints are tight at the optimum, which collapses the constrained problem into an unconstrained one:

Hinge-loss form
min 12 ‖w‖2 + C Σi max(0, 1 − yi(w⊤xi + b))

The hinge is zero once a point is correctly classified beyond the margin. Correct, confident points contribute nothing to the gradient, so the solution depends only on the support vectors near the boundary — the property that distinguishes it from log loss.

Spark's parameterisation inverts the usual intuition

LinearSVC minimises the averaged loss with an ℓ2 penalty scaled by regParam. Comparing forms gives C ↔ 1/(nλ) — so larger regParam means weaker regularisation in C terms, the opposite of what people expect.

LinearSVC is also linear-only in Spark: the dual needs an n × n Gram matrix, which at n = 4.5M is 2×1013 entries and hopeless. Scaling matters for exactly this reason — the penalty is not scale-invariant.

A3.4 Random Forest — bagging and parallel growth

Two independent randomisations decorrelate the trees. Bagging gives each tree a bootstrap resample; the probability a row is omitted is (1−1/n)n → e−1 ≈ 0.368, so each tree sees ~63.2% of distinct rows. Feature subspace sampling restricts each node to a random subset of features.

Why both randomisations are required
Var(avg) = ρσ2 + 1 − ρ B σ2

Adding trees drives the second term to zero but cannot touch the first. Only reducing the pairwise correlation ρ lowers the floor — and forcing different trees to consider different features at each node is what does that. Here DEPARTURE_DELAY is exactly the dominant predictor that would otherwise become the root split in nearly every bootstrap.

Parallel growth. The trees are conditionally independent given the data, so Spark does something better than one-tree-per-task: it grows all trees breadth-first, level by level. Each pass computes sufficient statistics for every node on the frontier across every tree, making the number of data passes O(depth) rather than O(B × depth).

A3.5 Gradient-Boosted Trees — sequential residual fitting

Stage-wise additive construction
Fm(x) = Fm−1(x) + ν hm(x)

where hm is fitted to the negative gradient of the loss at the current prediction. For squared error that gradient is the residual — which is where “fitting the residuals” comes from. It is the special case, not the definition.

Histogram binning. Exact split-finding would sort every value at every node — O(n log n) per feature per node, and a sort is a shuffle. Instead Spark discretises each continuous feature once into at most maxBins intervals via a sampled quantile sketch. Split finding then reduces to accumulating per-bin statistics: one pass, O(n), no shuffle. maxBins must also be at least the largest categorical arity — our grid uses 32 and 64 against a maximum of 24.

Why trees cannot be built in parallel. hm is fitted to residuals of Fm−1, so tree m cannot start before tree m−1 finishes — a genuine sequential dependency, unlike bagging's conditional independence. The parallelism is therefore within each tree: across partitions when accumulating histograms, and across features and bins when evaluating splits.

The result that matters — 14 arms, full data

Neither ensemble won. Linear regression took the regression task outright at R2 = 0.9289, against GBT's 0.8938 and Random Forest's 0.8731 — while costing 2.1× and 1.7× less wall-clock time.

Arrival delay is very nearly an affine function of departure delay. A single coefficient captures that exactly; both ensembles must approximate the same straight line with piecewise-constant regions, spending depth budget to do worse. Model capacity beyond the true functional form buys nothing, and axis-aligned splits are a poor basis for a diagonal relationship.

The linear model suffers most, by an order of magnitude. It has no way to recover a predictor rotated into a discarded component, whereas a tree can partially reconstruct the signal from whichever surviving components correlate with it. PCA is required by the brief, is defensible as decorrelation and compression — and here costs accuracy in six of the seven paired arms while also destroying feature-importance interpretability. The seventh is the Poisson GLM, which improves (−0.036 → 0.531): that arm is broken by its log link rather than by its features, and removing information simply lets it fail less badly. The two-arm design is what makes all of this visible rather than hiding it behind one reported number.

Classification: a tie decided on cost

GBT (0.9817), LinearSVC (0.9806) and Random Forest (0.9792) are separated by 0.0025 AUC — well inside what a different seed would move. But LinearSVC gets there in 959 s against GBT's 2,336 s, a 2.4× difference, for the reason derived in A3.5: boosting cannot parallelise across its trees, while a hinge-loss objective is convex and solved in a handful of distributed gradient passes. Thresholding at 30 minutes turns a near-linear regression surface into a near-linear decision boundary, so the simplest model finds it. On this data the ensembles are not buying accuracy — they are buying time.

Part B

How it runs in Spark

Everything above is mathematics that would be true in any framework. This part is the half that is only true in Spark: what MLlib's objects actually are, what happens to a flight as it moves through thirteen stages, and why the shape of the data changes the way it does.

B1 The MLlib contract

Three types carry the whole API, and the distinction between them is the thing that makes leakage structurally impossible rather than merely discouraged.

The three MLlib types
TypeHasHolds state?Example here
Transformertransform(df)no — pure function of a rowHaversineTransformer
Estimatorfit(df) → Modelno — it learns oneTargetEncoder
Modeltransform(df)yes — frozen at fit timeTargetEncoderModel

The detail that does the work

Model is a subclass of Transformer. So an Estimator/Model pair still satisfies “subclass Transformer” — while making it impossible to recompute learned state at transform time, because a Model has no fit to call. Quantiles, category means and standard deviations are frozen the moment fit returns. The test split physically cannot influence them.

A Pipeline is itself an Estimator; fit returns a PipelineModel, which is a Transformer. That recursion is why the whole thirteen-stage chain saves as one object and reloads with every learned number intact.

Where Spark differs from scikit-learn

In scikit-learn, transform() returns transformed data. In Spark it returns a new DataFrame describing a plan — nothing has been computed. Catalyst folds all thirteen stages into one optimised job, and the work begins only when an action demands a result.

This is why a bug can sit silent for twenty lines and then surface all at once, and why fit() is where every distributed pass actually happens. It is also why stage order matters for correctness but not for I/O: the rows are read once.

B3 How the data changes shape

A single flight enters as a CSV line and leaves as one number. The width changes six times on the way, and every change has a reason.

The counter-intuitive step

Feature engineering makes the data wider before anything makes it narrower: 24 columns become 80 slots. One-hot encoding is the reason — four categorical columns become sixty indicator slots, of which exactly four are set per row. The vector is 28.75% dense, and that sparsity is precisely what withMean=False exists to protect (A1.2).

B4 What every slot means

“An 80-dimensional vector” is not one thing — it is five blocks laid end to end. Verified slot by slot against six real flights:

Thirteen slots for twelve months

OneHotEncoder infers its category count from the largest value it observes and has no way to know the values start at 1. A maximum of 12 makes it assume indices 0…12 — thirteen categories — and reserve a slot for a month that cannot exist. DAY_OF_WEEK is the same (7 → 8); DEP_HOUR escapes it because hour 0 is midnight and genuinely occurs.

Those two dead slots, plus the StringIndexer bucket reserved for an unseen airline, are exactly the three columns VarianceThresholdSelector removes — which is where 80 → 77 comes from, and why PCA decomposes a 77×77 covariance rather than an 80×80 one.

B5 RowMatrixPCA, step by step

A2.1 established that the covariance never reaches the driver. This is the loop that achieves it. ARPACK uses reverse communication: it is never handed a matrix, only asked to be handed a product.

One Lanczos iteration
WhereWhat happensData moved
1driverdsaupd yields a vector v and asks for A⊤A v—
2→ executorsv is broadcast616 B
3each partitionaccumulates Σ ai(ai⊤v) over its own rowsrows never move
4tree reducetreeAggregate merges the partial vectors pairwise616 B each
5→ driverone vector returns; dsaupd produces the next v616 B

Two things this table is claiming

The largest object on any machine, at any moment, is a 616-byte vector. There is nowhere for an n×n matrix to exist. That is the literal reading of the specification's “without collecting full covariance matrices to the Driver node”.

The loop is not a batch loader. Every iteration scans all 5,704,000 rows and returns a complete product. Nothing is partial and nothing carries over; the only thing that differs between turns is v. Iteration is required because eigenvectors have no closed form — not because the data is being consumed in pieces.

That is also the cost: ~19 iterations means ~19 full passes, which is the measured 6.7–8.0× against the Gramian route.
