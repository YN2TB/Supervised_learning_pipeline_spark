Inside the Delay Pipeline

A walk through every moving part of this codebase — what Spark is doing underneath, what each formula is for, and why the pipeline is built the way it is. Written to be read start to finish, with the parts you can poke at marked try it.

Part 1 Orientation

What this project actually does

One sentence, then the numbers behind it.

You have a table of every commercial flight in the United States in 2015 — 5,819,079 rows of them. Each row records a flight: which airline, which airports, when it was scheduled, when it actually pushed back from the gate, and how many minutes late it eventually landed.

The project builds a machine that answers one question:

The question

A plane has just lifted off. Given only what we know at that instant — the airline, the route, the weather-free schedule facts, and how late it left the gate — how many minutes late will it land?

That "at that instant" is the whole game, and Part 3 explains why. A model that peeks at what happened after takeoff can score almost perfectly and be completely worthless.

There are really two questions, and the code answers both. The regression task predicts the number of minutes. The classification task predicts a yes/no: will this land more than 30 minutes late?

Part 2 The engine

How Spark works at all

Four ideas. Everything confusing about Spark comes from not having one of them.

Idea 1 — the data is cut into pieces

A pandas DataFrame is one table in one process's memory. A Spark DataFrame is a table that has been chopped into partitions, and the partitions are handed out to workers that each hold only their slice.

Nobody ever holds all 5.7 million rows. When you write df.filter(...), that filter is shipped to every worker and each one applies it to the rows it happens to be holding.

Idea 2 — nothing runs until you ask for an answer

This is the one that trips everybody. When you write a chain of Spark operations, nothing happens. Spark just writes down what you asked for. Only when you demand an actual result — a count, a saved file, a row printed — does it look at the whole recipe, optimise it, and run it.

Operations that just get recorded are called transformations. Operations that force the work to happen are called actions.

Build a chain, then run it

try it

Add steps and watch the clock stay at zero. Spark is only taking notes.

Why you should care

Laziness is why Spark can be fast. Because it sees the whole chain before running anything, it can rearrange it — push your filter down to the file read so it never loads the rows you were going to throw away. It is also why a bug can sit silently in your code for twenty lines and only explode at the .count().

Idea 3 — some operations make the data move, and those are the slow ones

Adding a column is cheap: every worker can do it to its own rows without talking to anyone. Spark calls this narrow.

Grouping is expensive. To compute the average delay per airline, every row for Delta has to end up on the same worker — so rows fly across the network to be regrouped. This is a shuffle, and it is almost always the reason a Spark job is slow.

Narrow versus wide

try it

Same three partitions, two different operations. Watch which one makes rows change home.

You can see this decision in your own config. spark_session.py sets spark.sql.shuffle.partitions, which is simply how many pieces to cut the data into when a shuffle happens. Spark's default is 200. On 5.7M rows and 16 cores that makes lots of tiny slices with more overhead than work, so the project sets it lower.

Idea 4 — caching, and its price

Because Spark is lazy, asking for two different answers from the same chain computes that chain twice. .cache() tells Spark to keep the result in memory after the first pass.

This project measured it rather than assuming, and found something worth knowing:

Measured, not guessed

Caching made fit faster — 51 s down to 35 s. But it made transform 23× slower — 0.28 s up to 6.5 s — because every cross-validation fold pays that cost on every pass. That is why MaterializeCache is an Estimator whose Model does nothing: the caching helps during fitting and then gets out of the way.

Part 3 data_prep.py

Getting the data honest

Two problems in the raw file, one of which will silently destroy your results if you miss it.

The leak — the single most important idea in the project

The raw table has columns like ARRIVAL_TIME, AIR_TIME, and five columns that break the delay down by cause: AIRLINE_DELAY, WEATHER_DELAY, and so on.

Those five columns add up to the answer. Feed them to a model and it scores R² ≈ 1.0, because you handed it the target written in five pieces. It has learned addition, not delay.

The fix is to fix a moment in time and refuse anything from after it. This project picks wheels-off — the instant the plane leaves the ground.

How to know it worked

At the wheels-off horizon, expect R² between 0.85 and 0.93. Near 0.99 means a leak got back in. Near 0.48 means a feature transform is destroying DEPARTURE_DELAY. Your best model scores 0.9289, right where honest work lands.

The October problem

Every month in the file identifies airports by their letter code — SEA, MCO. Except October, which uses numeric Department of Transportation ids — 14747, 13204.

Join that against the airports table and October matches nothing. You lose 486,165 rows, and Spark tells you nothing, because a join that finds no match is not an error.

scripts/build_airport_code_map.py recovers the mapping from the data itself: it finds the same flight numbers in other months, takes a majority vote on which letter code that route uses, and then verifies each guess geometrically — the recovered coordinates must reproduce the row's own published distance.

The subtle bit

Verification had to be done per code, not pooled. Pooled, the median error looked excellent — 0.96 miles — while five individual mappings were badly wrong. An average can hide the failures it is averaging.

CSV in, Parquet out

The last thing data_prep.py does is write the cleaned table as Parquet instead of CSV. This matters more than it sounds.

CSV is text: to read one column, Spark parses every character of every row. Parquet is columnar and typed — ask for three columns and it physically reads only those three off the disk. The tournament re-reads this data dozens of times, so the conversion pays for itself many times over.

Part 4 custom_transformers.py

Transformers, and why some are Estimators

The distinction that keeps the whole project honest.

MLlib has exactly two kinds of pipeline step.

A Transformer knows everything it needs in advance. "Take the log of this column" needs no knowledge of your data — it just does the arithmetic.

An Estimator has to learn something first. "Clip outliers" needs to know where the outliers are, and that depends on the data. So an Estimator has a fit() that looks at the training data and produces a Model — a Transformer with the learned numbers frozen inside it.

Worth defending out loud

The assignment brief says to subclass Transformer. Your OutlierIQRTruncator and TargetEncoder are Estimator/Model pairs instead. That is deliberate: implemented as bare Transformers they would refit on test data and on every streaming micro-batch. The report explains the choice — turning a spec ambiguity into an argument you can win.

The five custom steps

1. HaversineTransformer — how far apart are these airports?

The table gives coordinates, not distance. The great-circle distance between two points on a sphere is:

d = 2R · arcsin( √( sin²(Δφ/2) + cosφ₁ · cosφ₂ · sin²(Δλ/2) ) )

with φ latitude, λ longitude, R the Earth's radius. The arcsin-of-a-square-root form is used rather than the textbook cosine formula because it stays numerically accurate for short flights, where the plain version loses precision.

Two more features come out of it: route detour (published miles ÷ great-circle miles — how far from a straight line the airways force you) and schedule speed (miles ÷ scheduled hours — a leg scheduled at an implausibly high speed has no slack, so any delay goes straight through to arrival).

This is the Arrow part

This step is a @pandas_udf. Normally, running Python on Spark data means converting each row into a Python object, one at a time. A pandas_udf ships whole batches across in Apache Arrow's binary format — 20,000 rows at a time here — so the trigonometry runs once over a NumPy array at C speed instead of 5.7 million times through the interpreter.

2. OutlierIQRTruncator — tame the extreme values

A few flights left 15 hours late. Those rows drag a linear model badly. The classic fix is Tukey's fences: take the middle 50% of the data, and treat anything more than 1.5 of those widths outside it as an outlier.

IQR = Q₃ − Q₁     fences = [ Q₁ − 1.5·IQR , Q₃ + 1.5·IQR ]

Fitted on your training data, that gives DEPARTURE_DELAY fences of [−23, 25] minutes and TAXI_OUT fences of [−1, 31] minutes. Values outside get pulled to the fence rather than deleted — the row still has useful information in its other columns.

Computing an exact quantile of 4.5 million distributed values would need a full sort. Spark uses approxQuantile instead, which streams a compact summary and guarantees the answer is within a set relative error — 0.001 here.

3. SignedLog1pTransformer — squash the long tail

Distance is heavily right-skewed: many short hops, a few very long hauls. Taking a log compresses that. But log1p breaks on negative numbers, and delays are legitimately negative when a flight is early. So the signed form:

f(x) = sign(x) · log(1 + |x|)

which is exactly log1p for positive values and stays smooth and increasing across zero.

4. TargetEncoder — turn 4,627 routes into one number

One-hot encoding ROUTE would add 4,627 columns. Instead, replace each route with the average delay observed on that route. The danger is rare categories: a route flown three times, all of them disastrous, would get an extreme value from almost no evidence.

So the average is smoothed toward the global average:

encoded = ( Σy + m · prior ) / ( n + m )

where n is how many flights that category has, prior is the global mean delay, and m is how much evidence you demand before you trust the category's own average. Your fitted model uses m = 20 and a prior of 4.417 minutes.

Part 5 mllib_pipeline.py

Turning columns into one vector

MLlib models take exactly one input: a column of vectors. Six stages get you there.

After the custom steps you still have ordinary columns — some numbers, some text. Every MLlib algorithm wants a single column called features where each row holds one vector. The rest of the pipeline is about building that.

One-hot encoding, and why the vector is mostly zeros

StringIndexer turns "Delta" into a number, and OneHotEncoder turns that number into a vector that is all zeros except a single 1. Do that for airline, month, weekday and departure hour and most of your feature vector is zeros. Spark stores it sparsely — only the positions that are non-zero.

Scaling — and the decision that looks like a bug

Features arrive on wildly different scales: distance in the thousands, delay in the tens. A linear model's regularisation penalty would then punish them unequally. Standardisation fixes that:

z = (x − μ) / σ

But your code sets withMean=False — it divides by σ and skips subtracting μ. That looks like an oversight. It is the single most defensible line in the file.

What subtracting the mean does to a sparse vector

try it

Every zero minus a non-zero mean becomes non-zero. The sparse vector stops being sparse.

PCA — required, and it costs you

Principal Component Analysis finds the directions along which the data varies most, and keeps only the top k. Here k = 10.

Doing it on distributed data without ever collecting the matrix to one machine is the clever part: each worker computes the covariance contribution of its own rows, those get summed up a tree, and only the small resulting matrix goes to the driver for the actual eigen-decomposition.

What your 10 components actually captured

hover

Real values from docs/benchmarks/pca_explained_variance.json.

The honest result

Ten components retain only 28.5% of the variance, and the cost shows up in the score: linear regression falls from R² 0.9289 without PCA to 0.7034 with it. PCA is required by the brief, so the project runs both arms for every model — and the no-PCA arm is also the only one that can give you interpretable feature importances, because PCA's components are blends with no real-world meaning.

Why VarianceThresholdSelector sits just before PCA

It is not tidying. One-hot encoding with handleInvalid="keep" creates slots that are always zero. A constant column has zero variance, which makes the covariance matrix singular, and Spark's PCA dies with NotConvergedException. Dropping zero-variance columns first is what stops that.

Part 6 The results

The tournament

Seven model families, two arms each, one identical split.

Cross-validation

To choose hyperparameters you need to score them without touching the test set. So the training data is split into 5 folds: train on 4, score on the 1 held out, rotate, average. CrossValidator(numFolds=5, parallelism=4) runs four of those fits at once.

Searching a grid over 4.5 million rows takes many hours, so the search runs on a 91,144-row sample and only the winner is refitted on the full 4,564,168 training rows. The ranking of hyperparameters settles long before the metric value does.

What the scores mean

RMSE

Typical error in minutes, with big misses punished extra. Lower is better.

MAE

Average error in minutes, all misses weighted the same. The most human-readable number.

R²

Share of the variation explained. 1.0 is perfect, 0.0 is no better than always guessing the average.

AUC-ROC

For the yes/no task: the chance the model ranks a genuinely late flight above an on-time one.

Why the simplest model won

Plain linear regression beat two gradient-boosted ensembles, which surprises people. It should not.

Arrival delay is nearly a straight line in departure delay — the correlation is 0.947. A plane that leaves 40 minutes late lands roughly 40 minutes late. Linear regression models a straight line exactly. Trees have to approximate one with a staircase of splits, and never quite land on it.

The trees also cost twice the wall-clock time to lose.

The bug this nearly hid

Because that relationship is so nearly linear, anything that distorts DEPARTURE_DELAY destroys the model. Measured on this data: clipped gives R² 0.390, log-transformed 0.409, raw 0.937. That is why the raw column is passed through untouched alongside its clipped version. It looks untidy and it is worth 0.5 of R².

Effectively a three-way tie on accuracy — so the tiebreak is cost. LinearSVC reaches the same place in 959 seconds instead of 2,336. When models are indistinguishable on quality, the cheap one wins.

The GLM is bad, and that is a finding

The Poisson GLM scores R² −0.036 without PCA — worse than guessing the average. This is not a bug. A log link assumes the response is multiplied by its predictors, but arrival delay is added to departure delay. The link function does not match the physics. Naming that correctly is worth more than quietly dropping the arm.

MLflow — the lab notebook

Every arm logs its parameters, metrics, timings and the fitted model to MLflow, stored in mlflow.db. The winner is registered by name and promoted through Staging to Production, which is what lets inference.py ask for "whatever is in production" rather than a file path.

The trap that has already bitten once

Your system Python 3.14 carries MLflow 3.8.1. One command from it silently migrates mlflow.db to a schema the pinned 2.19.0 then refuses to open, and all 14 runs become unreadable. Always source ./env.sh first — even for a one-line query.

Part 7 inference.py

Serving the model

Proving the saved pipeline works on data it has never seen, with no retraining.

The whole 13-stage pipeline saves as a single object, with every learned number inside it — the IQR fences, the 4,627 route averages, the scaler's standard deviations, the regression coefficients. inference.py loads that one object and applies it to a stream of arriving flights.

Structured Streaming here is the same DataFrame API you already know. You call spark.readStream instead of spark.read, and Spark re-runs your query every time new files land, tracking what it has already processed in a checkpoint.

Two things that are easy to get wrong

A stream cannot guess its schema. A batch read can peek at the file; a stream has no file yet. So the training run publishes models/input_schema.json and the stream reads its column layout from there.

Custom classes must be importable when the model loads. The saved metadata refers to your transformers by name, so Python must be able to find custom_transformers.py — which is why submit_pipeline.sh passes --py-files custom_transformers.py.

A subtlety worth knowing about

If a GLM ever wins the tournament, its predictions come back shifted, because a log link needs a strictly positive target and the label was shifted by 88 minutes to make it so. inference.py reads the winning label from the schema file and undoes the shift. Without that, every served number would be 88 minutes too high — and still look like a plausible delay, so nothing would alert you.

Part 8 Hands on keyboard

Running it yourself

In order. The first line is not optional.

Every session starts here

# Git Bash
source ./env.sh
# PowerShell
. .\env.ps1

This pins the project's own JDK 17, the Hadoop native libraries, and the Python 3.11 interpreter. Your machine's defaults are all wrong for Spark and fail in confusing ways — a Java version Spark cannot use, a Python that crashes on import, a missing DLL that only breaks when you save a model.

Check the runtime is sane

python scripts/smoke_test.py        # must print 5/5
python scripts/test_transformers.py # must print 8/8

If smoke_test passes, Java, Arrow and model-saving all work. If it fails, stop — nothing downstream will work either.

A fast end-to-end run

python mllib_pipeline.py --sample-fraction 0.01 --tune-fraction 0.5 \
    --folds 2 --models linear_regression

A few minutes, and it exercises the entire path. Do this before any long run. Bugs that only appear at small scale are real ones — the PCA singularity was found exactly this way.

The streaming demo — two terminals

source ./env.sh && python inference.py
# terminal 2
source ./env.sh && python scripts/make_stream_events.py --batches 5

Redraw the charts without retraining

python benchmark_results.py
Two things that will waste an afternoon

Never type bare python. Without env.sh you get system Python 3.14, and if it touches mlflow.db your results become unreadable.

Part 9 Defence

Questions you will get asked

The nine most likely, with answers you can say out loud.

Why is your R² only 0.93 and not higher?

Because it is honest. The model predicts at wheels-off, using nothing that happens after takeoff. Anything above about 0.95 at this horizon means a leak got back in — the five *_DELAY columns literally sum to the target, so including them gives R² near 1.0 and a model that cannot predict anything.

Why does simple linear regression beat gradient boosting?

Because the underlying relationship really is close to linear — arrival delay correlates 0.947 with departure delay. Linear regression represents a straight line exactly; trees approximate one with a staircase and take twice as long to do it worse. The right model is the one that matches the shape of the data, not the most powerful one available.

You were told to subclass Transformer. Why are two of yours Estimators?

Because a Transformer that computes its own quantiles would recompute them on the test set and on every streaming micro-batch, which is a data leak. Fences and category means are learned parameters, so they belong in a Model produced by fit(). The report documents the deviation and the reasoning.

Why is withMean=False? Isn't standardisation supposed to centre the data?

Normally yes. But after one-hot encoding this feature vector is mostly zeros and stored sparsely. Subtracting a non-zero mean turns every zero into a non-zero, so the vector densifies — about 3.3× the memory here, on 5.7 million rows. Dividing by the standard deviation gives the scale-equalising benefit and preserves the zeros.

Your PCA only keeps 28.5% of the variance. Isn't that a failure?

It is a real cost, and the project reports it rather than hiding it: R² drops from 0.9289 to 0.7034. That is the honest answer to "should you always reduce dimensions" — no. PCA was required, so both arms were run, and the comparison is itself the finding. The no-PCA arm also gives interpretable feature importances, which PCA's blended components cannot.

Why does the GLM perform so badly?

Structural mismatch, not a bug. A log link models a response that gets multiplied by its predictors. Arrival delay is added to departure delay. The link function encodes the wrong arithmetic, so the model is fighting the data. An identity link would fix it; the mismatch is documented as a finding.

Where is Arrow used, and why does it matter?

In HaversineTransformer, via two @pandas_udf functions. Without Arrow, running Python on Spark data converts one row at a time into Python objects. Arrow ships 20,000-row batches in a binary columnar format, so the trigonometry runs once over a NumPy array in C rather than 5.7 million times through the interpreter.

Why did you run two arms for every model instead of just picking one?

Because the brief requires PCA and PCA measurably hurts here. Running both is what turns that tension into evidence: seven paired comparisons, PCA losing every one, with the cost quantified per model. One arm would have been either non-compliant or dishonest.

Can I just re-run it to reproduce your numbers?

Only at the same core count. randomSplit draws independently per input partition, and a Parquet read makes one partition per core — so the same seed gives a different split on a different machine: 16 cores gives 4,564,168 training rows, 8 gives 4,563,188, 4 gives 4,562,867. The tournament ran at local[*]. Anything reconstructing that split must call mllib_pipeline.make_split() at the same core count, and scripts/check_split.py asserts it has not moved.
